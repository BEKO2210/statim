# Soak run 1 (24 h, 2026-10-01): failed, and the protocol for run 2

READINESS P1 #23 asks for a 24 h soak with an RSS ceiling and a `/ready` poll. Run 1 **failed** two of
its nine checks, which were fixed before it started. This page records the result as it came out,
what the data shows, and the protocol for run 2, which is fixed here before run 2 starts.

Raw data: [soak-2026-10-01/soak.json.gz](soak-2026-10-01/soak.json.gz), with a sample every 30 s and
every unexpected response. The report written by `bench/soak.py` is
[soak-2026-10-01/soak.md](soak-2026-10-01/soak.md).

## What the data shows

**RSS: warm-up, not a leak.** These are the hourly RSS medians from `series` in the raw data:

| Hour | 0 | 1 | 2 | 4 | 8 | 12 | 16 | 20 | 23 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Median RSS, MiB | 2,677 | 2,864 | 2,984 | 2,946 | 2,967 | 2,963 | 2,949 | 2,987 | 2,953 |

- From hour 2 to hour 23 the least-squares slope is **+1.19 MiB per hour**, and hour 23 is 1 % below
  hour 2. Over 72 h that slope would add 86 MiB (3 %).
- Open file descriptors (10) and threads (44) did not change after start-up.
- The check compares the first hour after a 10-minute warm-up with the last hour, so it includes
  the allocator and engine pools filling up during hours 0 to 2.

The criterion was fixed before the run, and the run failed it. Run 2 does not reinterpret run 1.

**422: the load was above capacity.** Six closed-loop clients sent requests continuously to two
workers, so every request queued behind others. The median latency of a 200 was 18.8 s and its p95
61.5 s, against a 120 s inference deadline (queue wait included). 30 requests waited past the
deadline. The raw data keeps only the first 20 unexpected responses, and all 20 are batches (5 of
them through an adapter). Under overload the server answered them with its
documented 422 ([RUNBOOK.md](../RUNBOOK.md)) and stayed up, ready and healthy. Run 1 was meant to
test stability, not overload, which READINESS #24 covers. The load was set wrong for that purpose.

## Run 2: protocol, fixed before it starts

Run 2 covers both READINESS #23 (24 h) and #53 (72 h with cancellations and adapter switches).
**One 72 h run closes both items if it passes every check below. If it fails any check, neither
item closes.** The results go to `soak-<start date>.md` next to this page, whatever they show.

| | Run 2 | Change from run 1, and why |
|---|---|---|
| Binary | `statim` from main at `b97f581`, release flags | current code, including cancellation, single-open GGUF loading, and the key-length check |
| Server | as run 1 | — |
| Clients | **2** closed-loop clients | one per worker: the server is busy but nothing waits in its queue, so the 422 check tests stability, not overload |
| Warm-up | **120 min** | run 1's RSS rose for 2 h, then stayed flat |
| Duration | **72 h** | READINESS #53 |
| Checks and thresholds | unchanged: every answer 200 apart from cancellations, server up, /ready and /health 200, RSS growth ≤ 5 % (first hour after warm-up against the last hour), RSS max ≤ 6,144 MiB, fds +10, p95 drift ≤ 1.25×, SIGTERM exits 0, no sanitizer report | — |
| Seed | 20261001 (default) | — |
